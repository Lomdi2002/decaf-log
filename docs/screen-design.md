# Decaf Log 画面設計書

## 0. この文書の目的

本書は、`requirements.md` に定義された機能を、React上でどのような画面として実装するかを定義する。

Claude CodeはUI実装前に、

```text
docs/requirements.md
docs/screen-design.md
```

の両方を確認すること。

機能仕様について矛盾がある場合は `requirements.md` を優先する。

---

# 1. MVP画面一覧

Version 1.0では以下の3画面を実装する。

| ID      | URL        | 画面           |
| ------- | ---------- | -------------- |
| SCR-001 | `/`        | ダッシュボード |
| SCR-002 | `/record`  | カフェイン記録 |
| SCR-003 | `/history` | 摂取履歴       |

以下はMVPでは実装しない。

```text
/settings
```

設定画面はVersion 1.1以降。

---

# 2. 基本画面構成

スマートフォンを基本とする。

```text
┌────────────────────────┐
│       Decaf Log        │
├────────────────────────┤
│                        │
│                        │
│     Main Content       │
│                        │
│                        │
│                        │
├────────────────────────┤
│  Home  Record  History │
└────────────────────────┘
```

基本構成：

```text
Header
↓
Main
↓
Bottom Navigation
```

---

# 3. 共通レイアウト

## Header

全画面上部に表示。

表示内容：

```text
Decaf Log
```

MVPでは複雑なロゴを用意する必要はない。

アプリ名が明確に認識できればよい。

---

# 4. Bottom Navigation

全主要画面で使用する。

項目：

```text
ホーム
記録
履歴
```

遷移：

```text
ホーム
→ /

記録
→ /record

履歴
→ /history
```

現在表示中の項目は他の項目と区別できるようにする。

React Routerの `NavLink` 等を利用してよい。

モバイルでは画面下部へ固定してよい。

ただしコンテンツがBottom Navigationの裏へ隠れないこと。

---

# 5. UI基本方針

キーワード：

```text
シンプル
落ち着いている
清潔感
読みやすい
操作しやすい
```

以下を優先する。

1. 今日の摂取量が分かる
2. 記録ボタンがすぐ見つかる
3. 履歴が読みやすい
4. フォームが入力しやすい

不要な装飾や高度なアニメーションは実装しない。

# 6. レスポンシブ方針

## スマートフォン

基本：

```text
1カラム
```

画面幅いっぱいを利用するが、左右には適切な余白を設ける。

## PC

コンテンツを中央に配置する。

例：

```text
┌────────────────────────────────────┐
│                                    │
│          ┌──────────────┐          │
│          │              │          │
│          │   Content    │          │
│          │              │          │
│          └──────────────┘          │
│                                    │
└────────────────────────────────────┘
```

最大幅目安：

```text
600〜700px程度
```

厳密な値はClaude Codeが適切に判断してよい。

# 7. SCR-001 ダッシュボード

## URL

```text
/
```

## 目的

ユーザーがアプリを開いて、

- 今日のカフェイン摂取量
- 最近の記録
- 記録画面への導線

をすぐ確認できるようにする。

# 9. 今日のカフェインカード

必須表示：

```text
今日のカフェイン
```

合計値：

```text
130 mg
```

数値はダッシュボードで最も目立つ情報の一つとする。

記録がない場合：

```text
0 mg
```

---

# 10. 最近の記録

最新の記録を表示する。

MVPでは最大3件程度でよい。

各記録に表示：

- 飲み物名
- カフェイン量
- 時刻

例：

```text
コーヒー

100mg     10:00
```

日時の新しい順に表示する。

---

# 11. 「すべて見る」

最近の記録セクションに、

```text
すべて見る
```

を配置する。

押下：

```text
/history
```

へ遷移。

---

# 12. メインCTA

ダッシュボードには目立つ位置へ、

```text
＋ カフェインを記録
```

ボタンを配置する。

押下：

```text
/record
```

へ遷移。

主要操作なので、補助リンクより目立つデザインとする。

---

# 13. ダッシュボード Loading状態

初期データ取得中：

```text
読み込み中...
```

を表示する。

ユーザーが「画面が壊れている」と感じない表示にする。

---

# 14. ダッシュボード Error状態

取得失敗：

```text
データの取得に失敗しました。
もう一度お試しください。
```

可能であれば、

```text
再読み込み
```

操作を提供してよい。

---

# 15. ダッシュボード Empty状態

当日の記録がない場合：

```text
今日のカフェイン

0 mg
```

最近の記録も存在しない場合：

```text
今日はまだ記録がありません。

カフェインを記録してみましょう。
```

CTA：

```text
＋ カフェインを記録
```

を表示。

# 18. 飲み物入力

ラベル：

```text
飲み物
```

入力方式：

テキスト入力。

MVPではselectやプリセットにしない。

例：

```text
コーヒー
```

入力必須。

エラーは入力欄の近くへ表示する。

---

# 19. カフェイン量入力

ラベル：

```text
カフェイン量
```

入力方式：

数値入力。

右側または近くへ、

```text
mg
```

を表示する。

例：

```text
100 mg
```

0以上。

---

# 20. 摂取日時

ラベル：

```text
摂取日時
```

初期値：

現在日時。

ユーザーが変更できる。

HTMLの適切な日時入力コントロールを利用してよい。

---

# 21. 登録ボタン

表示：

```text
登録
```

フォーム内で最も目立つボタンとする。

正常入力時：

```text
登録
↓
Supabaseへ保存
↓
成功
↓
/
```

登録処理中は二重送信を防止する。

例：

```text
登録中...
```

としてボタンを一時的に無効化してよい。

---

# 22. キャンセル

表示：

```text
キャンセル
```

押下：

```text
/
```

へ戻る。

入力内容は保存しなくてよい。

---

# 23. フォームエラー

## 飲み物未入力

```text
飲み物を入力してください。
```

## カフェイン量未入力

```text
カフェイン量を入力してください。
```

## 負数

```text
0以上の数値を入力してください。
```

エラーは対象入力欄の直下または近くへ表示する。

---

# 24. 登録失敗

Supabaseへの登録失敗：

```text
記録の登録に失敗しました。
もう一度お試しください。
```

可能な限り入力内容を保持する。

# 27. 表示順

履歴は、

```text
consumed_at DESC
```

とする。

つまり、

**新しい記録を上に表示する。**

---

# 28. 記録表示項目

1レコードにつき以下を表示する。

- 飲み物名
- カフェイン量
- 摂取日
- 摂取時刻
- 削除操作

例：

```text
コーヒー

100mg

10:00

削除
```

---

# 29. 日付グループ

可能であれば日付ごとにまとめて表示する。

例：

```text
2026/09/12

コーヒー   100mg   10:00
緑茶        30mg   15:00


2026/09/11

コーヒー   100mg   09:30
```

ただし、実装が過度に複雑になる場合、MVPでは単純な一覧表示でも要件を満たす。

日付グループはMVP完成を妨げてはならない。

---

# 30. 削除操作

各記録へ、

```text
削除
```

を設置する。

削除操作前に確認を行う。

例：

```text
この記録を削除しますか？
```

選択肢：

```text
キャンセル

削除
```

MVPでは `window.confirm()` を使用してもよい。

---

# 31. 削除成功

成功した場合：

- 対象記録を画面から削除
- Supabase上から削除
- ダッシュボードの合計値へ反映

必要であれば、

```text
記録を削除しました。
```

を短時間表示してよい。

---

# 32. 削除失敗

```text
記録の削除に失敗しました。
もう一度お試しください。
```

元の記録は画面上に残す。

│
├ pages/

│  ├ RecordPage.jsx

Claude Codeは既存コードの状況に応じて合理的な変更を行ってよい。

# 39. ボタン優先順位

## Primary

最も重要。

```text
＋ カフェインを記録

登録
```

## Secondary

```text
すべて見る

キャンセル
```

## Destructive

```text
削除
```

視覚的に役割を区別する。

具体的な色はClaude Code側でシンプルに決定してよい。

---

# 40. フォーム共通ルール

基本：

```text
ラベル

入力欄

エラー
```

の順。

例：

```text
カフェイン量

[ 100 ]

0以上の数値を入力してください。
```

placeholderだけをラベル代わりにしない。

---

# 41. アクセシビリティ最低要件

最低限以下を守る。

- inputとlabelを関連付ける
- button要素を適切に使用する
- キーボード操作可能にする
- 読めないほど薄い文字色を避ける
- 主要操作をアイコンだけに依存しない
- エラー内容を文字でも表示する

---

# 46. 最終デザイン判断

Claude Codeが細かなUI判断を行う場合は、

```text
分かりやすさ
>
操作性
>
一貫性
>
装飾
```

の順に優先する。

完成を遅らせるような過剰なデザイン作業は行わない。

Version 1.0では、

**「見栄えの良い最小限のプロダクトUI」**

を目標とする。
