# Decaf Log Version 1.6 開発準備 検討資料

Version 1.6「カフェイン記録編集機能」の開発準備として、`CLAUDE.md` / `docs/requirements.md` / `docs/screen-design.md` / `docs/implementation-plan-v1.5.md` / `docs/v1.5-implementation-report.md` / 現在のソースコード（`RecordForm.jsx`, `RecordList.jsx`, `RecordItem.jsx`, `HistoryPage.jsx`, `caffeineRecords.js`, `App.jsx`のルーティング）/ `supabase/schema.sql` ・ `supabase/migrations/` を確認した上で整理した検討資料。

**この時点ではまだ `docs/requirements.md` ・ `docs/screen-design.md` 本体、ソースコード、DBへの変更は行っていない。** 本書は実装着手前の提案・論点整理であり、§20の不明点についてユーザーの判断を得たのち、各ドキュメントへ反映し実装計画（`docs/implementation-plan-v1.6.md`）を作成する。

- 作成日: 2026-09-13
- 対象: Version 1.6「カフェイン記録編集機能」のみ（Version 1.7以降は対象外）
- ブランチ: `feature/v1.6-record-edit`
- **Version 1.6はこれまでのVersion 1.1〜1.5と異なり、`docs/requirements.md`のロードマップに既存の記載がない、今回新たに追加する仕様である**

## 重要な確認結果（先出し）

`supabase/schema.sql`を確認したところ、`caffeine_records`には明示的に

```sql
-- UPDATEはMVPでは使用しないため許可しない
revoke update
on table public.caffeine_records
from anon;
```

と記載されており、**UPDATE権限は意図的に剥奪されている。UPDATEポリシーも存在しない。** そのため、Version 1.6で記録編集機能を実装する場合、**GRANT UPDATE・UPDATE用RLSポリシー・migrationの追加が必須**であり、これは既存のセキュリティ方針（「caffeine_recordsはSELECT/INSERT/DELETEのみ公開」）を変更する重要な判断である。

## 2. 「記録編集」の機能要件（案）

新しいFR（例：FR-012 カフェイン記録編集）として整理する。

- ユーザーは`/history`の各記録から編集画面へ遷移できる
- 飲み物名・カフェイン量・摂取日時を変更できる（FR-001と同じ3項目）
- 保存・キャンセルができる
- 保存後は履歴一覧に反映される
- 編集結果は今日の合計・目標進捗・日別グラフ・連続達成日数にも反映される
- 既存の削除機能はそのまま維持する

---

## 3. 編集対象となる項目

FR-001（新規登録）と同じ3項目のみ。新しい項目は追加しない。

- 飲み物名（`drink_name`）
- カフェイン量（`caffeine_mg`）
- 摂取日時（`consumed_at`）

---

## 4. 編集画面のURL・画面構成（未確定・要確認）

**案A（推奨）：専用ルート `/records/:id/edit`**

- `/record`（新規登録）と対になる、独立した1画面
- 既存の`RecordForm`と同様のフルページフォームレイアウトを踏襲でき、モバイルファーストの方針と一致する
- `RecordItem`に既存の「削除」ボタンと並べて「編集」ボタン（`/records/:id/edit`へのリンク）を追加する

**案B：`/history`内でのインライン編集（モーダルまたは展開フォーム）**

- 新しいルートは不要だが、`HistoryPage`の状態管理（どの記録を編集中か）が複雑になりやすい
- 一覧表示のレイアウトを崩しやすく、`screen-design.md`のシンプルさ重視の方針とはやや相性が悪い

**現時点では案Aを推奨するが、確定仕様ではないため§20で改めて確認する。**

## 5. 対象レコードの取得方法

`src/lib/caffeineRecords.js`に新しい関数`fetchRecordById(id)`を追加する想定。

```js
export async function fetchRecordById(id) {
  const { data, error } = await supabase
    .from('caffeine_records')
    .select('*')
    .eq('id', id)
    .single()

  if (error) {
    throw error
  }

  return toRecord(data)
}
```

現在のSELECTポリシーは`using (true)`（全行閲覧可）のため、このクエリは追加のRLS変更なしで動作する（SELECTに関しては変更不要）。

---

## 6. UPDATE処理の設計

`caffeineRecords.js`に`updateRecord(id, { drinkName, caffeineMg, consumedAt })`を追加する想定。

```js
export async function updateRecord(id, { drinkName, caffeineMg, consumedAt }) {
  const { data, error } = await supabase
    .from('caffeine_records')
    .update({
      drink_name: drinkName,
      caffeine_mg: caffeineMg,
      consumed_at: consumedAt,
    })
    .eq('id', id)
    .select()
    .single()

  if (error) {
    throw error
  }

  return toRecord(data)
}
```

`created_at`は更新対象に含めない（登録日時は変更しない）。

---

## 7. DB構造変更が必要か

**不要。** `drink_name`・`caffeine_mg`・`consumed_at`は既存カラムであり、新しいテーブル・カラムの追加は必要ない。変更が必要なのは権限（RLS/GRANT）のみ。

---

## 8. GRANT UPDATEが必要か

**必要（重要な確認事項）。** 現在の`schema.sql`には明示的に`revoke update ... from anon;`という記述があり、UPDATE権限は意図的に剥奪されている。記録編集を実装するには、これを`grant update on table public.caffeine_records to anon;`に変更する必要がある。

**これは、`caffeine_records`に対してanonロールが実行できる操作がSELECT/INSERT/DELETEの3つからUPDATEを含む4つ（実質すべてのCRUD操作）に拡大することを意味する。** 認証機構がない現状では、公開URLとanon keyを知る誰でも既存データを書き換えられるようになる。

---

## 9. UPDATE用RLS policyが必要か

**必要。** 既存のSELECT/INSERT/DELETEポリシーと同様の形式で、以下のようなポリシーを追加する想定（案）。

```sql
create policy "Allow public update access to caffeine_records"
on public.caffeine_records
for update
to anon
using (true)
with check (true);
```

`user_id`による絞り込みがないため、既存の3ポリシーと同じく「誰でも全行を対象にできる」形にならざるを得ない。

---

## 10. migrationが必要か

**必要。** `supabase/migrations/`配下に、Version 1.6用の新しいmigrationファイル（例：`YYYYMMDDHHMMSS_add_caffeine_records_update.sql`）を追加し、§8・§9の内容（GRANT UPDATE、UPDATEポリシー作成）を記述する想定。`supabase/schema.sql`にも、実装完了時点で最新のDB全体像として反映する。

**この点はVersion 1.1（`app_settings`追加）以来のDB変更であり、直近のVersion 1.2〜1.5はいずれもDB変更が不要だった。** Version 1.6は「DB変更を伴う」という点で、直近4バージョンと性質が異なる。

---

## 11. 編集後に今日の合計・グラフ・連続達成日数へどう反映されるか

**特別な連携処理は不要と考える。** 現在の実装では、`DashboardPage`・`HistoryPage`はいずれもページ表示のたびに`fetchRecords()`でSupabaseから最新データを取得し直しており、グローバルなキャッシュや状態共有の仕組みを持っていない。そのため、

- 編集完了後に`/history`へ遷移すれば、`HistoryPage`は最新化された記録を再取得して表示する
- その後`/`へ移動すれば、`DashboardPage`も同様に最新データを再取得し、今日の合計・目標進捗（`GoalProgress`）・連続達成日数（`StreakCard`）はすべて自動的に編集後の値を反映する
- `/history`の日別グラフ（`DailyChart`）も、`HistoryPage`が再取得した`records`から都度再計算されるため、追加の実装なしで編集結果を反映する

既存のVersion 1.2〜1.4のロジック（`goalProgress.js`, `streak.js`, `dailyTotals.js`）自体には一切変更が不要という結論になる。

---

## 12. Loading / Error / Not Found状態

- **Loading**：編集対象のレコードを取得中は「読み込み中...」を表示（既存パターンを踏襲）
- **Error**：取得・保存に失敗した場合、既存の文言パターン（「データの取得に失敗しました。」「記録の更新に失敗しました。」等）でエラー表示
- **Not Found**：指定されたIDの記録が存在しない場合（削除済み・不正なURL直打ちなど）、専用の「指定された記録が見つかりませんでした。」等のメッセージと`/history`へ戻る導線を表示する想定（Supabaseの`.single()`は該当行がない場合エラーを返すため、これを検出して分岐させる想定）

---

## 13. 保存成功後の遷移先（未確定・要確認）

**`/history`を推奨する**（編集はそもそも履歴画面から始まる操作のため）。ただし、新規登録画面（`RecordForm`）は保存後に`/`（ダッシュボード）へ遷移する仕様のため、一貫性を優先して`/`にするという考え方もある。§20で確認する。

---

## 14. キャンセル時の挙動

変更を保存せず、`/history`へ戻る（`RecordForm`のキャンセル挙動と同じ考え方）。

## 15. バリデーション

FR-001と同じ内容を流用する想定。

- 飲み物名：未入力（空白のみ含む）はエラー
- カフェイン量：未入力、負数、数値として扱えない値はエラー
- 摂取日時：未入力、無効な日時はエラー

`RecordForm.jsx`の`validate`関数と同一ロジックになるため、共通化するか複製するかは実装計画で検討する（§20）。

## 17. Version 1.0〜1.5への影響

- `RecordItem.jsx`に「編集」ボタン/リンクが追加される（`screen-design.md`の「削除操作」の記載も更新が必要）
- `caffeine_records`のRLS/GRANTが変更されるため、**既存のSELECT/INSERT/DELETE機能（記録登録・履歴表示・削除）の権限には影響しないが、テーブル全体のセキュリティ方針が変わる**
- `DashboardPage`, `GoalProgress`, `StreakCard`, `DailyChart`, `SettingsForm`等、他バージョンのコードには変更不要（§11参照）
- 既存の削除機能（FR-004）はそのまま維持

## 18. テストすべきケース

- 編集画面を開くと、既存の値（飲み物名・カフェイン量・摂取日時）が正しく初期表示される
- 値を変更して保存すると、`updateRecord`が正しい引数で呼ばれる
- 保存成功後、指定した遷移先へ移動する
- バリデーションエラー（飲み物未入力・カフェイン量未入力・負数・数値として扱えない値・摂取日時未入力）
- キャンセルすると変更を保存せず戻る
- 存在しないID・削除済みレコードへのアクセスでNot Found状態になる
- 取得中はLoading状態、取得失敗時はError状態になる
- 保存失敗時はエラーメッセージを表示し入力内容を保持する
- 二重送信防止（送信中はボタン無効化）
- 編集後、履歴一覧・ダッシュボードに更新後の内容が反映される（回帰確認）
- 既存の削除機能が編集機能追加後も正常に動作する（回帰確認）

## 19. セキュリティ上の注意点（重要）

- 現状`caffeine_records`は認証なしでanonロールにSELECT/INSERT/DELETEを公開しており、「MVP・デモ用途に限定した暫定構成」として既に合意済みである。Version 1.6でUPDATEも追加すると、**認証なしでcaffeine_recordsに対する実質すべてのCRUD操作が可能な状態になる。**
- DELETEは記録が消えるため利用者本人が気づきやすい一方、**UPDATE（改ざん）はデータが不自然に書き換わっても気づきにくい**という性質があり、公開の暫定構成としてのリスクはDELETE単体より一段高いと考えられる。
- 対応方針としては、既存のREADME/requirements.mdの記載（「一般公開時はSupabase Auth + user_id単位のRLSへ移行する」）を踏襲し、Version 1.6でもこの制約を明記する想定。認証機能自体はVersion 1.6では追加しない。
- `with check (true)`とする以上、DB側のCHECK制約（`caffeine_mg >= 0`）以外の追加バリデーション（例：未来日時の摂取日時を禁止する等）はポリシー側では行わない。これはINSERTの既存ポリシーと対称的な扱い。

## 20. ユーザー判断が必要な事項

1. **編集画面の実装方式**：`/records/:id/edit`という専用ルート（推奨・案A）か、`/history`内でのインライン編集/モーダル（案B）か
2. **UPDATE用RLS/GRANTの追加を承認するか**：`caffeine_records`に対してanonロールへUPDATEを公開すること（§8・§9・§19）。これはVersion 1.6実装における最も重要な承認事項
3. **保存成功後の遷移先**：`/history`（推奨）か`/`か
4. **Not Found時の表示レベル**：専用の「見つかりません」メッセージを実装するか、汎用エラーメッセージで済ませるか
5. **バリデーションロジックの共通化**：`RecordForm`と編集フォームで検証関数を共有するか、独立してそれぞれ持つか
6. **`consumed_at`への追加制限の要否**：未来日時などを拒否する追加チェックを設けるか、既存のINSERT同様に特に制限しないか
