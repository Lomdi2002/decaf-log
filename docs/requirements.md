# 1. プロジェクト概要

## 1.1 アプリ名

**Decaf Log**

## 1.2 アプリ概要

Decaf Logは、ユーザーが日々摂取したカフェイン量を記録し、摂取量を把握することで、カフェイン摂取量の削減を支援するWebアプリである。

ユーザーは飲み物・カフェイン量・摂取日時を登録し、履歴や当日の合計摂取量を確認できる。

将来的には目標管理、グラフ、連続達成日数などを追加する。

## 1.3 開発目的

本プロジェクトの最優先目的は、

**実際に動作するWebアプリを完成させ、公開すること**

である。

プログラミング学習を目的とした過度な分割、冗長なコード、教育目的の実装は不要。

以下を重視する。

- シンプルな実装
- 安定動作
- 保守しやすい構成
- モバイルでの使いやすさ
- 必要十分なテスト
- MVPスコープの厳守
- デプロイ可能な状態

# 9. 機能要件

## FR-001 カフェイン摂取記録登録

ユーザーは以下を入力して記録できる。

- 飲み物名
- カフェイン量
- 摂取日時

### 飲み物名

必須。

文字列として保存する。

前後の不要な空白は除去する。

### カフェイン量

必須。

単位：

`mg`

0以上の数値のみ許可する。

負数は登録不可。

### 摂取日時

ユーザーが入力可能。

初期値は現在日時。

未設定の場合は現在日時を利用してもよい。

---

# 10. FR-002 データ保存

正常な入力内容をSupabaseへ保存する。

保存成功後：

1. 登録処理を完了する
2. ユーザーへ成功したことが分かる状態にする
3. ダッシュボードへ戻る
4. 新しい記録が画面へ反映される

登録失敗時：

- 入力内容を可能な限り保持する
- エラーメッセージを表示する

---

# 11. FR-003 履歴表示

Supabaseに保存されている記録を一覧表示する。

並び順：

**摂取日時の新しい順**

表示項目：

- 摂取日
- 摂取時刻
- 飲み物名
- カフェイン量
- 削除操作

---

# 12. FR-004 記録削除

履歴から記録を削除できる。

削除処理前にユーザーへ確認する。

削除成功後：

- Supabaseから削除される
- UIから対象データが消える
- 今日の合計値も再計算される

削除失敗時：

- 元の記録は画面上に残す
- エラーメッセージを表示する

---

# 13. FR-005 今日のカフェイン合計

当日のカフェイン摂取量を合計する。

対象：

ユーザーのローカル日付における当日分。

計算：

```text
当日の全 caffeine_mg の合計
```

例：

```text
コーヒー 100mg
緑茶      30mg
```

結果：

```text
130mg
```

ダッシュボードに大きく表示する。

記録がない場合：

```text
0mg
```

と表示する。

有効な日時として扱えない場合は登録不可。

# 16. Error状態

データ取得失敗：

```text
データの取得に失敗しました。
もう一度お試しください。
```

登録失敗：

```text
記録の登録に失敗しました。
もう一度お試しください。
```

削除失敗：

```text
記録の削除に失敗しました。
もう一度お試しください。
```

技術的なエラー内容をそのまま一般ユーザーへ表示しない。

必要であれば開発者向けにconsoleへ出力してよい。

---

# 17. Empty状態

## ダッシュボード

当日の記録が存在しない場合：

```text
今日はまだ記録がありません。
カフェインを記録してみましょう。
```

記録画面への導線を表示する。

## 履歴

記録が1件もない場合：

```text
まだ記録がありません。
カフェインを記録すると、ここに履歴が表示されます。
```

# 18. データベース

テーブル名：

```text
caffeine_records
```

## 必須カラム

| カラム        | 型の想定          | 必須 | 内容         |
| ------------- | ----------------- | ---: | ------------ |
| `id`          | uuid              |  Yes | Primary Key  |
| `drink_name`  | text              |  Yes | 飲み物名     |
| `caffeine_mg` | numeric / integer |  Yes | カフェイン量 |
| `consumed_at` | timestamptz       |  Yes | 摂取日時     |
| `created_at`  | timestamptz       |  Yes | 登録日時     |

## 制約

`caffeine_mg >= 0`

とする。

`created_at` はデータベース側で自動設定する。

---

# 19. JavaScript側データ形式

React内部では基本的にcamelCaseを利用してよい。

例：

```javascript
{
  id: "uuid",
  drinkName: "コーヒー",
  caffeineMg: 100,
  consumedAt: "2026-09-12T10:00:00+09:00",
  createdAt: "2026-09-12T10:01:00+09:00"
}
```

Supabaseとの境界ではsnake_caseとの変換が発生してよい。

# 20. Supabase

Supabase接続情報は環境変数から取得する。

使用例：

```text
VITE_SUPABASE_URL
VITE_SUPABASE_ANON_KEY
```

値をコードへハードコードしない。

`.env.local` をGitへコミットしない。

`.env.example` はGit管理してよい。

---

# 21. Supabaseセキュリティ

MVPではユーザー認証を必須機能としない。

ただし、公開環境で認証なしのユーザーに無制限なINSERT・DELETE権限を与える構成はセキュリティリスクがある。

Claude Codeは以下を守ること。

- RLSを無意識に無効化しない
- 公開書き込み可能なポリシーを勝手に作らない
- セキュリティ上重要な判断が必要な場合はユーザーへ説明する
- Auth機能を勝手にMVPへ追加しない

Supabase設定用SQLは可能であれば、

```text
supabase/schema.sql
```

として保存する。
