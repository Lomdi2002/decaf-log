## 5. fetchRecordByIdの実装内容

```js
export async function fetchRecordById(id) {
  const { data, error } = await supabase
    .from(TABLE_NAME)
    .select('*')
    .eq('id', id)
    .maybeSingle()

  if (error) {
    throw error
  }

  return data ? toRecord(data) : null
}
```

`.maybeSingle()`を使用することで、「該当0件（Not Found）」と「通信・取得エラー」を区別している。0件時は`{data: null, error: null}`が返るため`null`を返し、実際のエラー時は`throw`する。取得成功時は既存の`toRecord()`でcamelCase変換して返す。

## 6. updateRecordの実装内容

```js
export async function updateRecord(id, { drinkName, caffeineMg, consumedAt }) {
  const { data, error } = await supabase
    .from(TABLE_NAME)
    .update({
      drink_name: drinkName,
      caffeine_mg: caffeineMg,
      consumed_at: consumedAt,
    })
    .eq('id', id)
    .select()
    .single()

  if (error) {
    throw error
  }

  return toRecord(data)
}
```

更新payloadには`id`・`created_at`を含めていない（登録日時は変更されない）。エラー時は`throw`し、呼び出し側（`EditRecordForm`）でエラーメッセージを表示する。

## 7. EditRecordPage / EditRecordFormの実装内容

**EditRecordPage**（`/records/:id/edit`）

- `useParams()`でURLから`id`を取得し、マウント時に`fetchRecordById(id)`を呼ぶ
- 4つの状態を明確に区別して表示する
  - Loading：「読み込み中...」
  - Not Found：該当記録なし（後述）
  - Error（取得失敗）：「データの取得に失敗しました。もう一度お試しください。」＋「再読み込み」ボタン
  - 正常時：`EditRecordForm`に取得した記録を渡して表示

**EditRecordForm**

- 初期値は渡された記録から設定する。`consumedAt`は既存の`dateUtils.toDatetimeLocalValue()`を使ってローカルタイムゾーンの`datetime-local`値に変換する（UTC文字列の単純切り出しは行っていない）
- 送信時は`recordValidation.js`の`validateRecordInput`で検証し、エラーがあれば送信しない
- 保存中は入力欄・ボタンをすべて無効化し、二重送信を防止する
- 保存成功時は`/history`へ`navigate`する
- 保存失敗時はエラーメッセージを表示し、入力内容は保持したまま画面遷移しない
- 「キャンセル」ボタンは`updateRecord`を呼ばずに`/history`へ`navigate`する

## 8. Not Found処理

`fetchRecordById`が`null`を返した場合（該当記録が存在しない：削除済み・不正なIDなど）にのみ、以下を表示する。

- メッセージ：「指定された記録が見つかりませんでした。」
- 「履歴に戻る」リンク（`/history`へのLink）

通信エラー時の「データの取得に失敗しました。もう一度お試しください。」とは明確に別の分岐であり、`EditRecordPage.test.jsx`のTEST-621（通信エラー）・TEST-622（Not Found、通常エラーメッセージが出ないことも確認）・TEST-623（「履歴に戻る」リンクの遷移先）で区別して検証している。

## 9. 共通バリデーションの内容

`src/lib/recordValidation.js`の`validateRecordInput({ drinkName, caffeineMg, consumedAt })`を新設し、`RecordForm`（新規登録）と`EditRecordForm`（編集）の両方から利用する。

```js
export function validateRecordInput({ drinkName, caffeineMg, consumedAt }) {
  const errors = {}

  if (drinkName.trim() === '') {
    errors.drinkName = '飲み物を入力してください。'
  }

  if (caffeineMg === '') {
    errors.caffeineMg = 'カフェイン量を入力してください。'
  } else if (Number.isNaN(Number(caffeineMg)) || Number(caffeineMg) < 0) {
    errors.caffeineMg = '0以上の数値を入力してください。'
  }

  const consumedDate = new Date(consumedAt)
  if (consumedAt === '' || Number.isNaN(consumedDate.getTime())) {
    errors.consumedAt = '摂取日時を入力してください。'
  }

  return errors
}
```

Version 1.0のRecordFormが元々持っていたルールから一切変更していない（未来日時の禁止など、新しい検証ルールは追加していない）。

## 10. migrationファイルの内容とanonのUPDATE権限

`supabase/migrations/20260914120000_add_caffeine_records_update.sql`（**未適用のローカルファイル**）：

```sql
revoke update
on table public.caffeine_records
from anon;

grant update (drink_name, caffeine_mg, consumed_at)
on table public.caffeine_records
to anon;

drop policy if exists "Allow public update access to caffeine_records"
on public.caffeine_records;

create policy "Allow public update access to caffeine_records"
on public.caffeine_records
for update
to anon
using (true)
with check (true);
```

- **anonがUPDATE可能なカラム**：`drink_name` / `caffeine_mg` / `consumed_at` の3カラムに限定したカラムレベルのGRANT（テーブル全体へのUPDATE権限は付与していない）
- **`id` / `created_at`**：このGRANTの対象外であり、anonからは引き続きUPDATE不可
- RLSポリシーは行レベルのアクセス制御のみ（`using (true) with check (true)`）。カラムレベルの制限は上記GRANTで担保している
