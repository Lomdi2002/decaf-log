## 2. 実装した記録編集機能

- FR-012：既存のカフェイン記録（`caffeine_records`の1行）を編集できる機能を追加した
- `/history` の各記録に「編集」リンクを追加し、対象記録の編集画面へ遷移できる
- 編集可能な項目は `drink_name`（飲み物名） / `caffeine_mg`（カフェイン量） / `consumed_at`（摂取日時）の3つのみ
- `id`・`created_at`（登録日時）はUIからもDBからも変更できない
- 保存成功時は `/history` へ遷移し、削除・新規登録と同様に既存のfetch-on-mountパターンにより、履歴一覧・ダッシュボード（今日の合計・目標進捗・連続達成日数）・日別グラフへ自動的に反映される。`goalProgress.js` / `dailyTotals.js` / `streak.js` 等の既存計算ロジックは変更していない
- キャンセルすると、変更を保存せず `/history` へ戻る
- 保存中は入力欄・ボタンを無効化し、二重送信を防止する
- 新規登録（`RecordForm`）と同一の入力バリデーションを編集画面でも使用する

`docs/requirements.md`・`docs/screen-design.md`のVersion 1.6詳細仕様（FR-012、§86〜§90）はすべて満たしている。

## 3. `/records/:id/edit`

- URL：`/records/:id/edit`（`:id`は編集対象の`caffeine_records.id`）
- `EditRecordPage`が`useParams()`でURLから`id`を取得し、マウント時に`fetchRecordById(id)`を呼び出す
- 取得成功時は`EditRecordForm`に記録を渡して表示する。`consumedAt`の初期値は`dateUtils.toDatetimeLocalValue()`でブラウザのローカルタイムゾーンの`datetime-local`値へ変換している（UTC文字列の単純切り出しは行っていない）
- 直接URLアクセス・ブラウザ更新（リロード）でも同様に動作する（Production環境での確認済み）

## 4. Not Found対応

該当する記録が存在しない場合（削除済み・不正なIDなど）に、通信エラーとは明確に区別したNot Found状態を表示する。

- `fetchRecordById`は`.maybeSingle()`を使用し、該当0件の場合は`{data: null, error: null}`が返るため、これを`null`として返す（実際の通信・取得エラー時は`throw`する）
- `EditRecordPage`は`fetchRecordById`が`null`を返した場合にのみ以下を表示する
  - メッセージ：「指定された記録が見つかりませんでした。」
  - 「履歴に戻る」リンク（`/history`）
- 通信エラー時のメッセージ（「データの取得に失敗しました。もう一度お試しください。」）とは別の分岐であり、両者が混同されないことをテスト・Production確認の両方で検証済み

## 6. UPDATE対象3カラム

`caffeine_records`に対するanonロールのUPDATE権限を、テーブル全体ではなく以下の3カラムに限定したカラムレベルGRANTとして追加した。

- `drink_name`
- `caffeine_mg`
- `consumed_at`

`updateRecord`の更新payloadにも、この3項目のみを含めている（`id`・`created_at`は含めていない）。

---

## 7. id / created_atはUPDATE不可

- `id`・`created_at`は上記GRANTのカラムリストに含まれていないため、`anon`ロールからは引き続きUPDATEできない
- Supabase本番DBに対してREST API経由で`id`・`created_at`のUPDATEを直接試行し、いずれも`42501 permission denied for table caffeine_records`で拒否されることを確認済み

## 8. Supabase migration内容

`supabase/migrations/20260914120000_add_caffeine_records_update.sql`（Supabase SQL Editorで手動適用済み）：

```sql
revoke update
on table public.caffeine_records
from anon;

grant update (drink_name, caffeine_mg, consumed_at)
on table public.caffeine_records
to anon;

drop policy if exists "Allow public update access to caffeine_records"
on public.caffeine_records;

create policy "Allow public update access to caffeine_records"
on public.caffeine_records
for update
to anon
using (true)
with check (true);
```

`revoke update` / `grant update (column list)` / `drop policy if exists` + `create policy` を使用しており、誤って複数回実行しても安全（冪等）。`supabase/schema.sql`にも同一の最終権限状態を追記済み（Version 1.0/1.1の既存ブロックは無変更）。

## 9. RLS / GRANT変更内容

| 項目 | 変更内容 |
| --- | --- |
| GRANT（カラムレベル） | `caffeine_records`の`drink_name` / `caffeine_mg` / `consumed_at`へのUPDATEをanonへ許可。テーブル全体へのUPDATE権限は付与していない |
| RLSポリシー（追加） | `Allow public update access to caffeine_records`（`for update to anon using (true) with check (true)`）。行レベルの制限はなし。カラムレベルの制限は上記GRANTで担保する |
| 既存のSELECT/INSERT/DELETEポリシー（Version 1.0） | 無変更 |
| `app_settings`のテーブル定義・RLS・GRANT | 無変更（Version 1.6由来の変更なし） |

Supabase本番DBへ適用後、REST API経由で以下を直接検証済み。

- `drink_name` / `caffeine_mg` / `consumed_at`のUPDATE：成功
- `id` / `created_at`のUPDATE：`42501 permission denied`で拒否
- `app_settings`のSELECT：成功、INSERT：引き続き拒否（Version 1.1から無変更）

## 10. セキュリティ上の既知の制約

- **認証なしでanonにUPDATEを許可している。** このアプリには認証機構がなく、公開URLとSupabase anon keyを知る誰でも既存記録を書き換えられる状態になる
- **UPDATE可能なのは `drink_name` / `caffeine_mg` / `consumed_at` の3カラムのみ。** テーブル全体へのUPDATE権限は付与していない
- **`id` / `created_at`はUPDATE不可。** カラムレベルGRANTの対象外であり、レコードの一意性・登録日時は改ざんできない
- **一般公開サービスとして提供する場合は、Supabase Auth + `user_id`単位のRLSが必要。** 現状は個人利用・デモ用途を前提とした暫定構成であり、複数ユーザーが同一データを共有する状態のまま
- **編集履歴・監査ログは未実装。** 誰がいつどの値からどの値へ変更したかを追跡する仕組みはなく、変更前の値を確認する手段もない
- 削除と異なり、書き換え（改ざん）はユーザー本人が気づきにくいという性質がある

Version 1.0〜1.5から引き続く制約（`caffeine_records`のRLSがMVP/デモ用途の暫定構成であること自体）は、Version 1.6でUPDATEが加わったことにより一段広がっている。詳細は`docs/requirements.md`のVersion 1.6セキュリティ上の既知の制約、および`README.md`のSupabaseのセキュリティに関する重要な注意事項を参照。

`docs/requirements.md`のVersion 1.6対象外に記載の通り、以下はVersion 1.6のスコープ外であり未実装のまま。

- Supabase Authによるユーザー認証、`user_id`単位のRLS
- 編集履歴・変更前の値の保存（監査ログ）
- 摂取日時（`consumed_at`）編集時の未来日時禁止などの追加バリデーション
- ユーザー独自の飲み物プリセット管理（追加・編集・削除）
- 目標値の履歴管理（Version 1.4から引き続く既知の制約）
- 通知、SNS連携、ダークモードなど（`docs/requirements.md` §7に記載のMVP対象外機能）

今後の拡張候補として考えられるもの（あくまで候補であり、着手が決まっているものではない）：

- ユーザー認証の導入（複数ユーザー対応、`caffeine_records`のRLSを本人の行のみ操作可能な構成へ変更）— Version 1.6でanonの権限がSELECT/INSERT/UPDATE(3カラム限定)/DELETEへ拡大したことにより、この移行の必要性は一段高まっている
- 編集履歴・監査ログの追加
- ユーザー独自のプリセット管理

各Versionは「実装 → テスト → 既存機能確認 → コミット」の順で進める方針（`docs/requirements.md` §28）を今後も踏襲する。
